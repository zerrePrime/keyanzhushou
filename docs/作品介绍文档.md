## 1. 作品简介

科研的日常是一条很长的链子：找文献、管文献、读懂文献、理清一个方向是怎么一步步发展起来的、找选题、写论文、做图表。每个环节今天都有工具，但工具之间不连通，数据要人来搬运。另一头，通用大模型直接回答学术问题并不可靠，它会把引用和结论一起编出来，用起来省事，核查起来更费事。

本作品把这条链子做进一个 Web 应用。用户上传自己的论文，系统负责解析、切块、入库；之后的每一个环节——问答、阅读、追新、图谱、写作——都围绕这个库展开，不是去互联网上临时抓取。设计上有一条贯穿全局的硬要求：**回答里的每个结论都要能指回原文的具体页码**。这条要求从检索、生成一直约束到前端呈现。

系统的核心是一个基于 LangGraph 的自主 Agent。它挂载了 8 个工具，模型自己决定调哪个、按什么顺序调，每一步的决策都记录在思考链里，前端可以逐步回放。用户既可以切到 Agent 模式让它规划，也可以直接点开某个功能模块单独使用。

## 2. 使用方式

打开访问地址，用评审账号登录后进入文献库。

**第一步，上传论文。** 点击上传，选择 PDF。系统自动完成版式解析、章节切块和向量化入库。上传过程中会显示真实传输进度和已用时间，大文件解析时也有明确的状态提示。重复的文件会被拦住，不会重复占用空间。

**第二步，提问。** 进入 RAG 问答，输入问题。回答正文下方会给出引用卡片，标注论文标题、页码和原文片段，点击可以跳到阅读器的对应页。如果库里没有相关内容，系统会明确告知资料不足，不会给出编造的回答。检索范围可以限定到某一篇论文。

**第三步，读原文。** 阅读器左侧是按版式还原的章节大纲，右侧是正文。选中一段、当前页或整篇，都可以调出中英对照翻译。

**第四步，看方向。** 引用图谱把库内论文的引用关系画出来，节点大小按 PageRank 排序。Agent 的「未来方向」工具会从论文的结论和局限里抽取可做的方向，并逐条判断是否已经被后来的工作做掉。

**第五步，追新。** arXiv 模块每天按提交时间倒序拉取最新论文，已经入库的会被过滤，检索结果里撞上库内论文的会打「已入库」标记。

**第六步，写。** 写作 Copilot 可以生成论文框架，也可以上传实验数据 CSV，自动识别数值列与类别列，一键切换七种图表，生成英文学术图注，导出 TikZ 或 Mermaid 代码。

## 3. 功能与亮点

### 3.1 细粒度解析与双层去重

解析不只是把 PDF 转成文本。系统用 PyMuPDF 抽取字号、粗体、版式方向，统计字号分布重建章节树，因此没有书签的 arXiv 论文、带页眉水印的出版版本都能识别。切块按八百字滑窗、一百字重叠，跨段落的句子不会被切断。

去重做了两层。第一层是文件级 MD5，同一个文件重复上传直接拒绝；第二层是语义级比对，针对「同一篇论文的 arXiv v1 到 v7」或者「重新导出后 MD5 变了」这类情况。做法是逐篇已有论文做精准比对，用 top-1 相似度均值衡量整体重合度，再按相同切块数量辅助解释，输出「高度重合」和「版本演进」两档，而不是简单的重复与否。

这一层在工程上还做了一次实打实的优化：原来先解析再算哈希，一本五百多页的书要先花几十秒解析，才发现是重复的。改成先算文件哈希、命中直接返回之后，重复文件检测从「先解析整本」降到 1.51 秒。

### 3.2 抗幻觉的四层设计

抗幻觉在这个作品里不是一个提示词，是四层机制叠起来的。

检索层设了距离阈值，不相关的内容进不来；检索结果为空时直接返回「找不到」，根本不进生成环节。生成层的提示词有三条硬约束：只根据资料回答、标注论文页码、资料不足必须明说。校验层做的是来源核对，Future Work 的来源标题必须能对上库内真实论文，对不上就不展示；判定「已解决」的方向必须有实际检索到的证据论文，判了却找不到证据的会自动降级为「部分解决」。呈现层把来源做成可点击的标签，用户可以随时跳回原文核验。

四层里最有价值的是第三层。多数 RAG 系统止步于「检索到就生成」，而这里的模型会先给出结论、再由代码去核对结论有没有依据，依据不足就把结论改弱。

### 3.3 能处理真实难度的长文档与扫描件

五百四十一页的整本教材可以完整解析，全量入库 1877 个切块，耗时七到八分钟，内存峰值 1.1GB。线上是一台 2 核 2G 的服务器，为此配了约 4GB swap，实测没有 OOM；nginx 的读取超时调到 1800 秒，覆盖这段长解析。

纯图片的扫描件没有文本层，系统会检测到文本为空并自动回退到 Tesseract 中英 OCR，识别后再切块入库。

### 3.4 引用图谱不是字符串匹配

图谱节点之间的边来自解析每篇论文的参考文献，再用词元重合度做实体对齐，重合度低于 0.75 的匹配直接丢弃。这条约束避免了「两篇论文标题都含 Attention 就被连起来」这类假边。

库内六篇论文形成 5 条真实引用边，还原了 Transformer 谱系的实际演进：Attention 引 Layer Normalization，GPT-3 引 BERT，ViT 引了其中三篇。节点大小按 PageRank 排，BERT 居首。

### 3.5 Agent 能接住指代，不做多余规划

多轮对话是 Agent 最容易露怯的地方。用户问完「有哪些可以做的方向」，接着说「把其中第一条翻译成英文」，句子里的「其中第一条」指向上一轮回答的内容，而这部分内容不在当前提问里。系统的处理是缓存上一轮的完整回答，检测到短问句里出现指代词时，把上一轮回答原文一并注入规划器，模型才能取到那一条。

另一个方向是收敛。简单问题只调一个工具就结束，不做多余的规划和总结，响应时间从 13 秒压到 4 秒左右。

### 3.6 数据到论文的最后一公里

上传 CSV 后系统自动判断列类型，类别列作横轴，数值列作序列，给出柱状、折线、面积、散点、饼图、相关性热力图等七种图表。图注由模型根据图表类型和统计摘要生成，拿到的是摘要而不是原始数据，编造具体数字的空间很小。除了图片，还能导出 TikZ 代码和 Mermaid 源码，前者是 LaTeX 原生绘图，投稿时比贴图片规范。

## 4. AI 技术落地使用情况

### 4.1 部署形态

作品已经部署在腾讯云轻量服务器上，公网可访问，不是本地跑的演示程序。容器由 docker compose 统一托管：后端跑 FastAPI/uvicorn，前端是 nginx 托管静态资源并反向代理 API。

LLM 走云端 OpenAI 兼容接口，因为 2G 内存跑不动本地 7B 模型；Embedding 仍是本地 ONNX MiniLM（384 维，23MB），CPU 推理没有压力。两者通过统一的调用层和 `LLM_PROVIDER` 环境变量切换，换模型不动业务代码。这一点决定了作品既能在一台没有外网的机器上完整跑通，也能在低配云服务器上对外提供服务。

Chroma、FastAPI、ONNX 常驻约 300–400MB，长文档解析时峰值 1.1GB。向量库目录和上传目录用 volume 挂载，容器重启不丢数据。

### 4.3 测试与压测

官方测试集的 10 个用例全部通过，覆盖上传解析、目录树、单页文本、版本演进识别、重复上传拦截、扫描件 OCR、长文档解析、RAG 问答、引用图谱和 arXiv 推荐。Agent 侧另外覆盖了 Future Work 的显式与隐式提问、中英互译、混合意图、多轮指代追问，以及库外话题拒答。

并发压测在 2 核 2G 的实例上做：3 篇 PDF 同时上传，期间再发起问答请求，12 次上传全部成功，没有 OOM、没有 5xx。问答在 CPU 满载时从 2 秒涨到 18 秒，但没有请求丢失，最终都返回了正确答案。这组数据说明系统在资源受限时的行为是降速而不是崩溃。

### 4.4 上线后暴露并修复的问题

线上验收时发现了一个只在真实环境下才会出现的问题：向量库元数据里有 2528 个切块，但 HNSW 索引只能命中 2211 个，缺失的 317 块正好属于四篇论文。原因是实例重启时索引写入不完整，而元数据和索引是分开持久化的。用已有向量重新 upsert 并重启服务后恢复。

这类问题在本地反复测试很难触发，它反映的是「元数据和索引需要一致性自检」这一工程事实。后续可以在服务启动时增加一次索引完整性检查。

### 5.2 三个自研算法

**语义级版本去重（top-1 mean）。** 逐篇已有论文比对，用 top-1 相似度均值衡量整体重合度，相同切块数量辅助解释。阈值 0.90 和 0.70 不是拍脑袋定的，是拿自比对、跨领域、同文不同版本三组数据实测校准出来的：自比对 1.0000，不同领域 0.50–0.57，Transformer v1 与 v7 在 0.95 以上。

**Future Work 时间线裁决。** 论文里写的 future work，可能已经被后来的工作做掉了，照着做就是重复劳动。系统把这件事拆成五步：多路查询挖掘方向；推断各论文发表年份并缓存；在每个方向的其他论文里检索相近片段，排除来源论文本身，距离小于 0.86 才算证据；用严格审稿人提示词逐条判定已解决、部分解决或仍开放；最后做幻觉校验，证据对不上就把结论降级。输出的是「还能不能做」，而不是一串看起来很有道理的方向。

**版式感知标题树。** 不依赖 PDF 书签，靠字号分布统计、粗体、排版方向和多模式噪声过滤重建章节结构，并额外过滤了书籍自带的目录页，避免把目录条目当成正文章节。

### 5.3 工程优化

展示类作品容易忽略延迟，但延迟直接决定能不能用。这一轮做了几处实测有效的优化。

arXiv 下载改成多线程分片：先发一个 256KB 的 Range 请求拿到文件总大小，再把剩余字节切 8 段并行拉取后合并。国际链路单连接只有 21KB/s，8 连接跑到 83KB/s，2.11MB 的 PDF 从 101 秒降到 26 秒；服务端不支持 Range 时自动回退单连接，不会把功能做坏。

语义去重原来对每篇已有论文都重复做一次 embedding 计算，现在先算一次新论文的向量，逐篇查询时传向量而不是文本，耗时从 37 秒降到 9 秒。

首屏原来同步加载 503KB 的 PDF.js，登录页必须等它下载完才能渲染。改成按需动态加载之后，首屏体积从 659KB 降到 159KB，PDF 阅读器只在打开时下载。
