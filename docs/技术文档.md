## 1. 项目概述

### 1.1 背景与目标

科研工作者在日常研究中面临一条完整而繁琐的链路：搜集文献 → 管理文献 → 精读文献（语言障碍）→ 梳理领域脉络 → 寻找研究切入点 → 撰写论文与绘制图表。每一步都有独立工具，但工具之间彼此割裂，数据无法流动，且通用大模型直接回答学术问题存在严重的幻觉风险（编造引用、编造结论）。

本项目的目标是构建一个**以大语言模型为核心、以本地文献库为事实基础的全流程科研助手 Agent**，将上述链路整合进同一个 Web 应用，并通过 LangGraph Agent 架构让模型**自主规划、自主调用工具**完成多步骤科研任务，同时以「抗幻觉 RAG + 源头溯源」机制保证每一个结论都可追溯到原文具体页码。

### 1.2 功能总览

系统包含六大功能模块与一个统一的 Agent 入口：

| # | 模块 | 核心技术 |
|---|------|---------|
| ① | PDF 管理与细粒度解析 | PyMuPDF 版式分析 + MD5/语义双层去重 |
| ② | 抗幻觉 RAG 问答 | Chroma 向量库 + ONNX MiniLM + 页码溯源 |
| ③ | 版式感知阅读 | 标题树导航 + 划词/整页中英对照翻译 |
| ④ | arXiv 自动检索推荐 | arXiv Atom API + 相关度排序 |
| ⑤ | 引用图谱挖掘 + 自动综述 | NetworkX + PageRank 基石论文识别 |
| ⑥ | 学术写作 + 数据可视化 | 论文框架生成 + CSV 智能图表 + TikZ/Mermaid 导出 |

统一 Agent 入口提供 8 个 Function Calling 工具，模型在 ReAct 循环中自主决定调用哪些工具、以什么顺序调用，并全程输出可折叠的思考链（thinking trace）。

### 1.3 技术栈与模型选型

| 层 | 选型 | 说明 |
|---|------|------|
| 前端 | Vue 3 + Vite + ECharts + PDF.js | 单页应用，8 个视图 |
| 后端 | FastAPI（Python 3.11+） | RESTful API，自动生成 OpenAPI 文档 |
| Agent 框架 | LangGraph（StateGraph） | ReAct 状态机，显式可控的循环结构 |
| LLM（本地） | qwen2.5:7b（Ollama） | 开发/有 GPU 环境默认，零 API 费用 |
| LLM（云端） | OpenAI 兼容协议（阿里百炼 qwen-plus 等） | 生产部署一键切换，代码零改动 |
| Embedding | Chroma 内置 ONNX all-MiniLM-L6-v2（384 维） | 本地推理，无需联网下载模型服务 |
| 向量库 | Chroma（HNSW，cosine 距离） | 持久化存储，随库自带 embedding function |
| PDF 解析 | PyMuPDF（fitz） | 文本/版式/字号/粗体等细粒度信息 |
| 图计算 | NetworkX | 有向引用图 + PageRank |

模型选型的核心考量：**全流程可本地闭环运行**（答辩现场无网可用），同时保留**云端大模型切换能力**（低配置服务器部署时获得更强回答质量），二者通过统一的 `llm_chat()` 调用层和 `LLM_PROVIDER` 环境变量切换。

## 2. 系统架构

### 2.1 三层架构

系统整体分三层，数据单向流动：

```
┌─────────────────────────────────────────────────────┐
│ 前端层  Vue 3 + Vite + ECharts + PDF.js             │
│         文献管理 / 问答 / 阅读 / 检索 / 图谱 / 写作 / Agent │
├─────────────────────────────────────────────────────┤
│ 服务层  FastAPI 路由 → 业务服务 / LangGraph Agent    │
│         论文服务 · RAG 问答 · 图谱服务 · CSV 服务     │
│         LLM 统一调用层（Ollama / OpenAI 兼容）        │
├─────────────────────────────────────────────────────┤
│ 数据层  Chroma 向量库（ONNX Embedding）              │
│         PyMuPDF 解析 · 本地文件存储                  │
└─────────────────────────────────────────────────────┘
```

**请求链路**：Vue 前端发起 HTTP 请求 → FastAPI 路由分发 → 直接进入业务服务，或由 LangGraph Agent 规划后按需调用工具 → 读写 Chroma 向量库 / 解析 PDF → 结果逐层返回前端渲染。

### 2.3 配置与 LLM Provider 抽象

所有配置经 Pydantic Settings 从 `.env` 读取（`extra: "ignore"` 保证向后兼容），敏感信息（API Key）**仅通过环境变量传入，不入库**。

LLM 统一调用层 `llm_chat(prompt, system)` 按 `LLM_PROVIDER` 分发：

- `ollama` → 本地 Ollama `/api/generate`（qwen2.5:7b，`num_ctx=8192`）；
- `openai_compatible` → 云端 OpenAI 兼容 `/chat/completions`（默认阿里百炼接入点，DeepSeek、硅基流动等同协议服务均可接入）。

切换成本为零：改两个环境变量即可，业务代码完全不变。这一抽象也是 2C2G 低配置云服务器部署方案的基础（见第 7 章）。

## 3. 核心模块实现

### 3.1 模块一：PDF 管理与细粒度解析

#### 3.1.1 结构化解析（PyMuPDF）

`pdf_parser.parse_pdf()` 对每篇上传的 PDF 提取：

- **paper_id**：文件 MD5 前 12 位，天然作为主键并支撑精确去重；
- **标题/作者**：扫描首页文本 span，取字号 ≥ 14 的首个文本为标题、下一行为作者（学术论文版式先验）；
- **正文切块**：全文拼接后按 **800 字符滑窗、100 字符重叠**切块，每块通过逐字符页码映射取**众数页**作为所属页——这是后续「页码溯源」的数据基础；
- **参考文献**：定位最后一个独立的 References/Bibliography 标题行后开始抽取，按条目末尾年份切分，最多 80 条存入向量库 metadata，供引用图谱使用。

#### 3.1.2 版式感知标题树（outline）

`extract_outline()` 基于**字号 + 粗体 + 排版方向**提取 H1/H2/H3 标题树，而非依赖 PDF 自带书签（大量 arXiv PDF 无书签）：

1. 以「行」为单位聚合 span，跳过旋转文本（水印、竖排页眉）；
2. 按字符数统计推断**正文字号**（出现字符最多的字号）；
3. 按字号相对正文的倍数分级：≥1.45 → H1，≥1.20 → H2，≥1.08 → H3；
4. **粗体短行兜底**：粗体、长度 ≤ 60、无标点的行也识别为小节标题，覆盖无字号差异的模板；
5. 多重噪声过滤：页码正则、邮箱、版权/许可关键词、首页标题区上方的页眉与下方的作者单位区。

该解析为实时进行、不写库，因此不影响已构建的向量库。前端阅读器据此渲染可点击的章节导航树。

#### 3.1.3 双层去重（MD5 精确 + 语义级）

上传时执行两层去重检测：

**第一层 · MD5 精确去重**：paper_id 已存在于库中 → 直接拒绝入库。

**第二层 · 语义级去重（top-1 mean 算法）**：文件内容有改动（重新导出、版本修订）时 MD5 失效，需要语义判断。对新论文的每个 chunk，分别在**每篇已有论文内向量检索 top-1 最相似 chunk**（`where={"paper_id": pid}` 精准限定），取所有 top-1 余弦相似度的**均值**作为两篇论文的整体相似度，并统计相似度 ≥ 0.98 的「几乎相同 chunk」数量。

阈值经实测校准：

| 场景 | top-1 mean | 判定 |
|------|-----------|------|
| 自比对（同一论文） | 1.0000 | —— |
| 不同论文 | ≤ 0.57，且无 chunk ≥ 0.9 | 不报告 |
| 同一论文 v1 vs v7 修订版 | ≥ 0.95 | 高度重合 |
| ≥ 0.90 | `high_overlap` | 提示「内容高度重合，建议确认不要重复入库」 |
| 0.70 ~ 0.90 | `version_evolve` | 提示「疑似版本演进（如 arXiv v1→v7），建议保留最新版本」 |

检测结果（相似度百分比、相同 chunk 比例、建议文案）随上传接口返回，前端弹出醒目的去重提示。语义命中时不阻断入库（用户可能确需对比两个版本），但给出明确警告，把决定权交给用户。

### 3.2 模块二：抗幻觉 RAG 问答

#### 3.2.1 检索管道

`retrieve_context()` 的检索策略：

- **中文查询翻译**：英文论文库 + 中文提问存在语言鸿沟。中文问题先由 LLM 翻译成一句简洁的英文学术检索语句（带进程内缓存，翻译失败或输出异常时回退内置中英关键词映射表），再用英文 query 检索，避免中英混排导致的检索漂移；
- **大库去偏**：候选池放大到 `max(top_k×6, 20)` 条，第一轮限制每篇论文最多贡献 2 条，不足 top_k 时再放开配额补足——防止数百页的教材把单篇论文的相关段落完全挤掉；
- **距离阈值过滤**：余弦距离 < 0.9 才纳入上下文，宁缺毋滥；
- **top_k=5**：兼顾相关性与上下文长度；传入 `paper_id` 时可把检索范围限定在指定论文内（单篇提问）。

#### 3.2.2 生成约束与源头溯源

`answer_with_sources()` 的 Prompt 硬性约束：

1. **只根据参考资料回答，不要编造**；
2. 回答里标出信息来自哪篇论文第几页；
3. 参考资料里没有答案时，必须明确说「资料不足，无法回答」。

检索不到任何相关段落时直接返回「文献库中找不到相关内容，请先上传论文」，**不给 LLM 自由发挥的机会**。返回结构中附带完整 sources 列表（paper_id、标题、页码、chunk 定位符），前端将来源渲染为可点击标签，点击即跳转到阅读器对应页面，形成「答案 → 证据 → 原文」的闭环验证路径。

#### 3.2.3 跨论文对比与分段翻译

- **多文对比**：`multi_paper_compare()` 扩大 top_k=10，按 paper_id 分组聚合各论文相关片段，Prompt 要求分点列出异同并给综合结论；
- **翻译**：划词/整页/整篇三级。长文本按空行段落聚合成 ≤1200 字符的段，逐段翻译，单次最多 12 段（超出标记 truncated，前端整篇翻译时按页分批调用）。系统提示词约束「只输出译文、保留公式变量与引用标记」，避免模型加解释或漏译。

### 3.3 模块三：版式感知阅读

前端阅读器（PDF.js 渲染）与后端解析能力联动：

- 左侧**章节导航树**：来自 3.1.2 的标题树，点击跳转对应页；
- **划词翻译**：选中文本调用翻译接口，弹层显示对照译文；
- **整页/整篇中英对照**：单页文本接口按页提取，逐页翻译后双栏联动滚动，541 页长文档亦可流畅使用；
- 问答页的来源标签可一键跳转至本模块对应论文对应页。

### 3.4 模块四：arXiv 自动检索推荐

`arxiv_service.search_arxiv()` 封装 arXiv 官方 Atom API：

- 相关度降序排序，可配置返回条数（默认 10）；
- 解析标题、作者、摘要（截断 300 字符）、更新时间、PDF 直链；
- `get_daily_papers()` 按「AI / ML / RAG / Agent」关键词聚合每日最新论文，做个性化推荐；
- 检索结果可**一键入库**：下载 PDF 走标准上传管道（含语义去重），外部检索与本地文献库打通；
- 15 秒超时 + 错误结构化返回，网络异常不拖垮 Agent。

### 3.5 模块五：引用图谱挖掘 + 自动综述

#### 3.5.1 真实引用边构建

`build_citation_graph()` 从向量库 metadata 中读出每篇论文的 references 列表，把每条参考文献与库内论文标题都做归一化分词，**被引标题的词元在参考文献行中的重合度 ≥ 75%** 才判定为引用；同时排除标题完全相同的不同版本（v1/v7/扫描件），避免把同一篇论文的副本连成假边。边标注 `method="title_match"`，一条 reference 最多匹配一条边，避免误连。

**降级策略**：若全部论文都没抽到参考文献（某些模板参考文献格式特殊），退化为全连接 baseline 图并明确标注 `edge_method="baseline_fallback"`，保证功能可用性同时不伪造引用关系。

#### 3.5.2 PageRank 基石论文识别

在有向引用图上运行 **PageRank（α=0.85）**，结合入度返回 Top 10 基石论文（pagerank 值 + 入度）。基石论文即「被库内其他论文广泛引用的工作」，帮助用户快速定位领域必读文献。前端用 ECharts 力导向图渲染节点与引用边。

#### 3.5.3 自动综述

`generate_auto_survey()` 先按标题去重，再从每篇论文中挑一段代表性正文（优先含 abstract 的段落与靠前页面，跳过版权页、目录、参考文献），按「起源、发展、前沿」三段式生成 150–300 字综述，并要求每个论断后标注所依据的论文标题。只喂标题会得到与库内文献无关的通用套话，喂正文片段才能让综述真正基于库内内容。

### 3.6 模块六：学术写作 + 数据可视化

#### 3.6.1 学术写作辅助

- **论文框架生成**：输入研究 idea，输出标题、摘要、引言、相关工作、方法、实验、结论七段式框架；
- **架构图生成**：文字描述 → Mermaid 代码，前端实时渲染；
- **图表 Caption**：基于图表对应的真实数据统计生成学术风格图注。

#### 3.6.2 CSV 智能图表化

`csv_service` 实现「上传 CSV → 自动理解 → 推荐图表 → 一键出图 → 导出论文可用格式」的完整链路：

1. **列画像**：自动推断每列类型（numeric / datetime / categorical / text），统计缺失值、唯一值、数值列的 min/max/mean；
2. **图表推荐**：按列类型组合推荐——有数值列则推荐表格/柱状/折线，≥2 个数值列追加散点/相关性热力图/雷达图，有类别列追加饼图；
3. **ECharts 配置生成**：`build_option()` 直接产出前端 `setOption` 可用的配置，支持 line / bar / pie / scatter / radar / heatmap 六种，热力图基于 pandas 相关系数矩阵；
4. **Figure Caption**：`data_summary()` 把数据压缩为统计摘要（规模、各列均值/极值、首尾变化趋势、前 5 行样例）喂给 LLM，生成**基于真实数据、不编造数字**的图注；
5. **导出**：图表可导出为 LaTeX TikZ 或 Mermaid 代码，直接插入论文源码。

安全细节：CSV 以随机 file_id 落盘，读取仅允许已保存的 id，杜绝路径穿越。

## 4. Agent 工具链与自主任务规划

### 4.1 LangGraph ReAct 状态机

Agent 基于 LangGraph `StateGraph` 构建，显式定义三个节点与循环边：

```
        ┌──────────┐    ┌───────────┐
        │  decide  │ →  │  execute  │ ──┐
        └──────────┘    └───────────┘   │ should_continue
              ↑                         │ （未 FINISH 且未达最大轮数 → decide；
              └─────────────────────────┘   否则 → synthesize）
        ┌────────────┐
        │ synthesize │ → END
        └────────────┘
```

- **decide（任务规划）**：把用户请求、已执行工具的结果摘要、剩余可用工具清单组装成规划 Prompt，要求 LLM 输出 `{"action", "query", "intent"}` JSON——选择下一个工具、**重写**传给该工具的查询（结合已有结果而非照抄原句）、说明理由；
- **execute（工具执行）**：按工具签名精确构造参数调用，记录耗时与结果摘要；
- **synthesize（汇总）**：把全部工具结果 + 工具串联链路交给 LLM 生成最终自然语言回答，要求体现多工具结果的综合结论并标注来源页码。

### 4.2 八个 Function Calling 工具

| 工具 | 能力 | 触发场景 |
|------|------|---------|
| `rag_qa` | 文献库抗幻觉问答，带页码溯源 | 问已上传论文的内容 |
| `arxiv_search` | arXiv 实时检索 | 问最新进展、前沿方向 |
| `graph_analyze` | 引用图谱 + PageRank 基石论文 | 问核心论文、领域脉络 |
| `auto_survey` | 自动生成领域综述 | 要求总结领域现状 |
| `write_framework` | 生成七段式论文框架 | 有研究 idea 要成文 |
| `list_papers` | 列出文献库论文 | 问库里有什么 |
| `future_work` | 提取未来方向并剔除已被解决的旧 idea | 问不足、选题灵感 |
| `translate` | 中英互译（支持「译成中文/英文」自然语言指定方向） | 要求翻译句子或段落 |

工具用 LangChain `@tool` 装饰器定义，docstring 即工具描述，直接参与规划 Prompt——**模型靠阅读工具描述自主决定调用顺序**，例如「帮我综述这个领域并找未来方向」会触发 `auto_survey → future_work → synthesize` 的多工具串联。

**最小必要工具原则**：一次库内检索已能回答的问题（如「某个概念是什么」）不再追加图谱/综述等重工具，避免过度规划；只有用户明确要求图谱、综述、未来方向、翻译等多步分析时才继续调用下一个工具。

**同义词路由**：规划 Prompt 内置同义词映射——limitation / 不足 / 展望 → `future_work`，翻译 / 译为 / 译文 → `translate`，最新 / 年份 → `arxiv_search`，降低模型因措辞差异漏调工具的概率。

### 4.3 决策鲁棒性设计

本地 7B 模型的 JSON 输出不稳定，`_parse_decision()` 提供多级兜底：

1. 剥离 markdown 代码围栏后优先按 JSON 解析；
2. JSON 失败 → 在纯文本中扫描剩余工具名 / FINISH / DIRECT 关键词；
3. 工具名非法或重复选择已执行工具 → 首轮默认回退 `rag_qa`，已有结果时强制 FINISH；
4. **双重终止保险**：最大迭代轮数（3 轮）+ 全部工具执行完毕，任一触发即进入汇总，**从机制上杜绝死循环**。

**DIRECT 路由**：通用知识问题（「XX 是什么」）不经过任何工具，由模型直接回答，但系统提示词要求「不确定时说不知道，不要假装引用了任何文献」——与 RAG 路径的抗幻觉策略保持一致，且避免对文献库的无效检索。

### 4.4 思考链与多轮记忆

- **思考链（thinking_trace）**：每一步记录 `{step, intent, tool, query, output_summary, output_full, elapsed_ms, status}`，前端默认折叠、点击展开，完整展示「为什么调这个工具、传了什么查询、拿到什么结果、耗时多少」——满足赛事对 Agent 决策过程可解释性的要求；
- **多轮记忆**：按 session_id 维护最近 10 轮用户输入，后 3 轮摘要注入规划上下文，支持「再查一下最新的」「换成柱状图」这类指代性追问；
- **溯源复用**：`rag_qa` 工具执行时的 sources 缓存后直接随 Agent 回答返回，不重复跑一次完整问答。

## 5. 抗幻觉设计体系

抗幻觉不是单点技巧，而是贯穿四个层次的体系：

| 层次 | 机制 |
|------|------|
| **检索层** | 距离阈值 0.9 过滤不相关内容；检索为空时直接返回「找不到」，不进入生成 |
| **生成层** | Prompt 三约束：只根据资料回答 / 标注论文页码 / 资料不足必须明说 |
| **校验层** | Future Work 的来源标题必须能对回库内真实论文（归一化模糊匹配），对不上不展示；`solved_by` 必须是实际检索到的证据论文，判「已解决」却无证据时自动降级为「部分解决」 |
| **呈现层** | 来源标签可点击跳转原文页，用户可即时核验；DIRECT 路径明确声明「不引用文献」 |

此外，Figure Caption 生成基于数据统计摘要而非自由发挥，从数据侧封死编造数字的空间。

## 6. 关键创新点

### 6.1 语义级版本去重（top-1 mean 算法）

针对「同一论文不同版本（arXiv v1→v7）、重新导出导致 MD5 变化」这一文献管理的真实痛点，设计了 per-paper top-1 相似度均值算法：逐篇已有论文精准比对、均值度量整体重合度、相同 chunk 计数辅助解释。阈值（0.90 / 0.70）经自比对、跨论文、版本对三组实测校准，并区分「高度重合」与「版本演进」两级语义化提示，而非简单的是/否二值判断。

### 6.2 Future Work 时间线去重

选题场景的核心问题：论文里提出的 future work，**可能已经被后续工作解决了**，照着做就是重复研究。本系统实现了完整的「挖掘 → 验证 → 裁决 → 校验」管道：

1. **挖掘**：多路查询（future work / limitations / conclusion / open problems）+ 提示词正则优先定位结论与展望段落，LLM 归纳 3–6 个带来源的方向；
2. **时间线**：LLM 推断各论文发表年份并本地缓存（`_paper_years.json`，仅首次有开销），归一化标题模糊匹配兜底；
3. **验证**：对每个方向在**其他论文**中检索相近片段（排除来源论文自身，距离 < 0.86），收集真实证据标题；
4. **裁决**：以「严格审稿人」Prompt 逐条判定 已解决 / 部分解决 / 仍开放；
5. **幻觉校验**：`solved_by` 必须能在证据论文中对上，否则判「已解决」自动降级——裁决结论同样不允许是幻觉。

最终输出「仍开放 / 部分解决」的可做方向清单，并把已被解决的旧方向单独列出说明由谁解决，配合论文时间线可视化，直接回答「这个 idea 还能不能做」。

### 6.3 版式感知标题树

不依赖 PDF 书签，基于字号分布统计 + 粗体 + 排版方向 + 多模式噪声过滤重建章节结构，对无书签的 arXiv PDF、带水印页眉的出版版本均稳健；粗体短行兜底规则覆盖了无字号差异的模板。

## 7. 部署方案

### 7.1 本地开发部署

```powershell
# 后端（Python 3.11+，需先启动 Ollama 并拉取 qwen2.5:7b）
cd backend && pip install -r requirements.txt
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000

# 前端（Node.js 18+）
cd frontend && npm install && npm run dev   # http://localhost:5173
```

### 7.2 Docker 部署

仓库内置 `docker-compose.yml`、`Dockerfile`、`nginx.conf`：

```bash
docker-compose up -d backend ollama                  # 后端 + 本地 LLM
docker-compose --profile serve-frontend up -d        # 前端静态资源走 nginx
```

### 7.3 低配置云服务器部署（公网方案）

针对 2 核 2G 云服务器（3 人左右轻量使用）：

- **LLM 走云端 API**：2G 内存无法运行本地 7B 模型，设置 `LLM_PROVIDER=openai_compatible` + `OPENAI_API_KEY` + `OPENAI_BASE_URL`（默认阿里百炼，可选 DeepSeek 等），应用代码零改动；Embedding 仍为本地 ONNX MiniLM（23MB，CPU 推理无压力）；
- **内存保障**：Chroma + FastAPI + ONNX 常驻约 300–400MB；541 页长文档全量解析时峰值约 1.1GB，配置 2GB swap 防止 OOM；
- **容器化部署**：docker compose 统一托管 backend（FastAPI/uvicorn）与 frontend（nginx 静态托管 + API 反向代理），`docker compose -f docker-compose.prod.yml up -d` 一键启动；
- **公网访问**：域名未备案，对外使用 8080 端口规避国内 80/443 限制；nginx 反代后端并为站点启用 Basic Auth，评审账号随提交材料提供；
- **长文档超时**：nginx `proxy_read_timeout` 调至 1800s，覆盖 541 页约 7–8 分钟的解析耗时；
- **数据持久化**：向量库目录与上传目录以 volume 挂载，随容器重启不丢失。

| 比对对 | top-1 mean | 相同 chunk（≥0.98） |
|-------|-----------|---------------------|
| 论文自比对 | 1.0000 | 全部 |
| 不同领域论文两两比对 | 0.50 ~ 0.57 | 0 |
| Transformer v1 vs v7 | ≥ 0.95 | 绝大多数 |

据此确定 0.90（high_overlap）与 0.70（version_evolve）两级阈值，误报率与漏报率均在可接受范围。

### 8.3 Agent 多工具串联验证

典型验证用例：

- 「这个领域有哪些核心论文？帮我总结一下现状」→ `graph_analyze → auto_survey → synthesize`，思考链完整记录两步决策；
- 「库里论文还有哪些可以做的方向？」→ `future_work`，输出仍开放方向 + 已排除方向及解决者；
- 「什么是注意力机制？」（通用问题）→ `DIRECT` 直接回答，不触碰文献库；
- 连续追问「最新进展呢」→ 多轮记忆生效，`arxiv_search` 被正确触发；
- 「把这些 limitation 翻译成中文」→ `future_work → translate → synthesize`，混合意图工具串联。

## 9. 局限与未来工作

### 9.1 已知局限

1. **扫描件 OCR 精度**：扫描件走 Tesseract 中英双语识别，低分辨率或复杂版式下存在字符错误，且版面标题树识别有限（目录可能为空），后续可换用 PaddleOCR 或版面分析模型提升；
2. **引用匹配精度**：references 采用词元重合度（≥75%）匹配，对缩写标题、同名变体仍存在漏配，可引入参考文献结构化解析（如 GROBID）提升；
3. **多轮记忆**：进程内字典实现，重启丢失，生产环境应换 Redis 等外部存储；
4. **年份推断**：Future Work 时间线依赖 LLM 推断年份，个别冷门论文可能不准，可接 arXiv/DOI 元数据校正。

### 9.2 规划方向

- 扫描件 OCR 换用 PaddleOCR / 版面分析模型，提升低质量扫描件识别率；
- 引用抽取引入 GROBID 等结构化解析，提升缩写标题与多作者文献的匹配精度；
- 更多图表类型（三维雷达图等）与批量实验数据对比模板。
