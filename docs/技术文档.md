## 1. 项目概述

### 1.1 背景与目标

科研的日常是一条长链条：找文献、管文献、读懂文献、理清一个方向怎么发展起来、找选题、写论文、做图表。每个环节现在都有工具，但工具之间不连通，数据要人工搬运。另一头，通用大模型直接回答学术问题并不可靠，它会把引用和结论一起编出来。

本项目把上述环节做进一个 Web 应用，以用户自己的文献库作为事实来源，用 LangGraph 组织一个能自主规划步骤、按需调用工具的 Agent。设计上有一条硬要求：回答里的每个结论都要能指回原文的具体页码。这条要求贯穿了后面的检索、生成和前端呈现。

### 1.2 功能总览

系统由六个功能模块和一个统一的 Agent 入口组成：

| # | 模块 | 核心技术 |
|---|------|---------|
| ① | PDF 管理与细粒度解析 | PyMuPDF 版式分析 + MD5/语义双层去重 |
| ② | 抗幻觉 RAG 问答 | Chroma 向量库 + ONNX MiniLM + 页码溯源 |
| ③ | 版式感知阅读 | 标题树导航 + 划词/整页中英对照翻译 |
| ④ | arXiv 自动检索推荐 | arXiv Atom API + 提交时间排序 + 库内去重 |
| ⑤ | 引用图谱挖掘 + 自动综述 | NetworkX + PageRank 基石论文识别 |
| ⑥ | 学术写作 + 数据可视化 | 论文框架生成 + CSV 智能图表 + TikZ/Mermaid 导出 |

Agent 入口提供 8 个 Function Calling 工具，模型在 ReAct 循环里决定调用哪些工具、按什么顺序调用，每一步的思考过程都会记录并展示在前端。

### 1.3 技术栈与模型选型

| 层 | 选型 | 说明 |
|---|------|------|
| 前端 | Vue 3 + Vite + ECharts + PDF.js | 单页应用，8 个视图（含登录页） |
| 后端 | FastAPI（Python 3.13） | RESTful API，自动生成 OpenAPI 文档 |
| Agent 框架 | LangGraph（StateGraph） | ReAct 状态机，循环结构显式可控 |
| LLM（本地） | qwen2.5:7b（Ollama） | 开发和有 GPU 的环境默认使用，无 API 费用 |
| LLM（云端） | OpenAI 兼容协议（阿里百炼 qwen-plus 等） | 部署到低配服务器时切换，业务代码不改 |
| Embedding | Chroma 内置 ONNX all-MiniLM-L6-v2（384 维） | 本地推理，不需要单独部署向量服务 |
| 向量库 | Chroma（HNSW，cosine 距离） | 持久化存储，自带 embedding function |
| PDF 解析 | PyMuPDF（fitz） | 可拿到文本、版式、字号、粗体等信息 |
| 图计算 | NetworkX | 有向引用图 + PageRank |

选型时主要考虑两点。全流程要能在一台没有外网的机器上跑完，答辩现场不至于卡在网络上；同时要能随时换成云端模型，2 核 2G 的服务器跑不动 7B 参数模型。这两点通过统一的 `llm_chat()` 调用层和 `LLM_PROVIDER` 环境变量兼顾，切换只改配置，不动业务代码。

### 2.1 三层架构

│ 前端层  Vue 3 + Vite + ECharts + PDF.js             │
│         文献管理 / 问答 / 阅读 / 检索 / 图谱 / 写作 / Agent │

│         会话鉴权 · 论文服务 · RAG 问答 · 图谱 · CSV   │
│         LLM 统一调用层（Ollama / OpenAI 兼容）        │
├─────────────────────────────────────────────────────┤

### 2.3 配置与 LLM Provider 抽象

配置统一由 Pydantic Settings 从 `.env` 读取，`extra: "ignore"` 保证多出字段不会报错。API Key 只从环境变量进入进程，不写进数据库，也不进代码仓库。

`llm_chat(prompt, system)` 按 `LLM_PROVIDER` 分成两条路径：

- `ollama`：调用本地 Ollama `/api/generate`，默认模型 qwen2.5:7b，`num_ctx=8192`；
- `openai_compatible`：调用云端 `/chat/completions`，默认阿里百炼，DeepSeek、硅基流动这类同协议服务也能直接接。

这两种部署形态共用同一套业务代码，也是第 7 章里 2C2G 公网方案能成立的原因。

## 3. 核心模块实现

### 3.1 模块一：PDF 管理与细粒度解析

#### 3.1.1 结构化解析（PyMuPDF）

`pdf_parser.parse_pdf()` 对每个上传的 PDF 提取四类信息。`paper_id` 取文件 MD5 的前 12 位，既是主键，也直接用于精确去重。标题和作者从首页的文本 span 里扫出来，字号 ≥ 14 的第一个文本当标题，下一行当作者，这条规则来自学术论文的常见版式。

正文全文拼接后按 800 字符滑窗、100 字符重叠切块，每块通过逐字符页码映射取出现次数最多的页，作为该块的所属页，页码溯源准不准就看这一步。参考文献在最后一个独立的 References/Bibliography 标题行之后开始抽取，按条目末尾年份切分，最多保留 80 条写进向量库 metadata，供引用图谱使用。

#### 3.1.2 版式感知标题树（outline）

`extract_outline()` 不读 PDF 自带书签，而是根据字号、粗体和排版方向重建 H1/H2/H3 标题树。arXiv 下载的 PDF 有相当一部分没有书签，靠书签的做法在这些文件上会直接失效。

1. 以行为单位聚合 span，跳过旋转文本，比如水印和竖排页眉；
2. 统计各字号出现的字符数，出现最多的字号判定为正文；
3. 按字号相对正文的倍数分级：≥1.45 为 H1，≥1.20 为 H2，≥1.08 为 H3；
4. 粗体短行兜底：粗体、长度不超过 60 字符、不带标点的行也视为小节标题，用来覆盖字号没有差异的模板；
5. 噪声过滤：页码正则、邮箱、版权与许可关键词，以及首页标题上方的页眉、下方的作者单位区。

这一步是实时解析，不写库，所以不影响已经建好的向量库。前端阅读器用它的结果渲染可点击的章节导航。

#### 3.1.3 双层去重（MD5 精确 + 语义级）

上传时依次做两层检测。

第一层是 MD5 精确去重。paper_id 已经存在就直接拒绝入库。

第二层针对内容有改动的情况。重新导出的 PDF、修订版本，MD5 都会变，精确去重拦不住。做法是把新论文的每个 chunk 在每篇已有论文内部做一次 top-1 检索（`where={"paper_id": pid}` 限定范围），取所有 top-1 余弦相似度的均值，作为两篇论文的整体相似度；同时统计相似度 ≥ 0.98 的 chunk 数量，用来解释重合的程度。

阈值是实测出来的：

| 场景 | top-1 mean | 判定 |
|------|-----------|------|
| 自比对（同一论文） | 1.0000 | —— |
| 不同论文 | ≤ 0.57，且无 chunk ≥ 0.9 | 不报告 |
| 同一论文 v1 vs v7 修订版 | ≥ 0.95 | 高度重合 |
| ≥ 0.90 | `high_overlap` | 提示「内容高度重合，建议确认不要重复入库」 |
| 0.70 ~ 0.90 | `version_evolve` | 提示「疑似版本演进（如 arXiv v1→v7），建议保留最新版本」 |

检测结果随上传接口返回，前端弹提示。语义命中时不阻断入库，因为用户有时确实需要对比两个版本，系统只负责把风险说清楚。

### 3.2 模块二：抗幻觉 RAG 问答

#### 3.2.1 检索管道

`retrieve_context()` 做四件事。中文提问先用 LLM 转成一句英文学术检索语句再去检索，因为库里都是英文论文，直接拿中文问会有语言偏差；译文带进程内缓存，翻译失败或输出异常时回退到内置的中英关键词映射表。

候选池放大到 `max(top_k×6, 20)`，第一轮限制每篇论文最多贡献 2 条，不够 top_k 再放开配额补足。不加这个限制，一本几百页的教材会把单篇论文的相关段落全挤出去。余弦距离小于 0.9 的片段才进上下文，宁可少给几条。默认 `top_k=5`，兼顾相关性和上下文长度；传入 `paper_id` 时检索范围限定在该论文内，用于单篇提问。

#### 3.2.2 生成约束与源头溯源

`answer_with_sources()` 的 Prompt 给了三条硬约束：

1. 只根据参考资料回答，不要编造；
2. 回答里标明信息来自哪篇论文第几页；
3. 参考资料里没有答案时，明确说「资料不足，无法回答」。

检索阶段如果一条都没命中，系统直接返回「文献库中找不到相关内容，请先上传论文」，不把问题交给模型。返回结构里带完整 sources 列表（paper_id、标题、页码、chunk 定位符），前端渲染成可点击标签，点一下跳到阅读器对应页。这样用户核对证据时不用自己翻页。

#### 3.2.3 跨论文对比与分段翻译

多篇对比时 `multi_paper_compare()` 把 top_k 提到 10，按 paper_id 分组聚合片段，Prompt 要求先分点列出异同再给综合结论。翻译支持划词、整页、整篇三种粒度，长文本按空行段落聚合成不超过 1200 字符的段，逐段送模型，单次最多 12 段；超出部分标记 `truncated`，前端整篇翻译时按页分批调用。系统提示词限定只输出译文、保留公式变量与引用标记，避免模型加解释或漏译。

### 3.3 模块三：版式感知阅读

阅读器用 PDF.js 渲染，和后端解析能力配合。左侧章节导航树来自 3.1.2 的标题树，点击跳到对应页；选中文本调翻译接口，弹层显示对照译文。整页和整篇支持中英对照，按页取文本、逐页翻译后双栏联动滚动，541 页的教材也能正常翻。问答页的来源标签点一下，直接跳到本模块的对应论文和页码。

### 3.4 模块四：arXiv 自动检索推荐

`arxiv_service` 封装 arXiv 官方 Atom API。检索结果按相关度降序，条数可配，默认 10 条，解析出标题、作者、摘要（截断到 300 字符）、更新时间、PDF 直链。`get_daily_papers()` 用 AI / ML / RAG / Agent 等关键词聚合当天最新论文，按 `submittedDate` 倒序取 20 篇，剔除库内已有的，被过滤的条数通过 `skipped_count` 返回给前端展示。

检索结果可以直接入库：下载 PDF 后走标准上传管道，语义去重照样生效，外部检索和本地库是打通的。请求设 15 秒超时，异常时返回结构化错误，不会把 Agent 卡死。

### 3.5 模块五：引用图谱挖掘 + 自动综述

#### 3.5.1 真实引用边构建

`build_citation_graph()` 从向量库 metadata 读出每篇论文的 references，把每条参考文献和库内论文标题都做归一化分词。被引标题的词元在参考文献行里的重合度达到 75% 才判定为引用。标题完全相同的不同版本（v1/v7、扫描件）会被排除，避免同一篇论文的副本连出假边。边上一律标 `method="title_match"`，一条 reference 只匹配一条边。

如果所有论文都没抽到参考文献（部分模板的参考文献格式比较特殊），系统退化为全连接 baseline 图，并在返回值里标 `edge_method="baseline_fallback"`。这样做是保证功能不至于空白，同时不伪造引用关系。

#### 3.5.2 PageRank 基石论文识别

在有向引用图上跑 PageRank（α=0.85），结合入度返回 Top 10 基石论文。所谓基石论文，就是被库内其他论文反复引用的那几篇，通常也是这个方向绕不开的必读文献。前端用 ECharts 力导向图渲染节点和边。

#### 3.5.3 自动综述

`generate_auto_survey()` 先按标题去重，再从每篇论文里挑一段代表性正文，优先取含 abstract 的段落和靠前页面，跳过版权页、目录和参考文献页，最后按「起源、发展、前沿」三段式生成 150–300 字综述，并要求每个论断后面标出所依据的论文标题。

这里踩过一个坑：只喂标题的话，模型会输出一段和库里文献没什么关系的通用套话；必须喂正文片段，综述才真正落在库内内容上。

### 3.6 模块六：学术写作 + 数据可视化

#### 3.6.1 学术写作辅助

学术写作这块有三个小功能。给一个研究 idea，输出标题、摘要、引言、相关工作、方法、实验、结论的七段式框架；用文字描述架构，转成 Mermaid 代码在前端实时渲染；图表 Caption 则根据图表背后的真实数据统计生成学术风格图注。

#### 3.6.2 CSV 智能图表化

`csv_service` 完成「上传 CSV → 理解数据 → 推荐图表 → 出图 → 导出论文可用格式」这条链路：

1. **列画像**：推断每列类型（numeric / datetime / categorical / text），统计缺失值、唯一值，以及数值列的 min/max/mean；
2. **图表推荐**：按列类型组合推荐。有数值列就推荐表格、柱状图、折线图；两个以上数值列再追加散点图、相关性热力图、雷达图；有类别列则追加饼图；
3. **ECharts 配置生成**：`build_option()` 直接产出前端 `setOption` 能用的配置，支持 line / bar / pie / scatter / radar / heatmap 六种，热力图基于 pandas 相关系数矩阵；
4. **Figure Caption**：`data_summary()` 把数据压缩成统计摘要（规模、各列均值与极值、首尾变化趋势、前 5 行样例）再交给 LLM，让图注基于真实数字，而不是模型的自由发挥；
5. **导出**：图表可导出为 LaTeX TikZ 或 Mermaid 代码，直接插进论文源码。

安全上，CSV 以随机 file_id 落盘，读取时只接受已保存的 id，避免路径穿越。

## 4. Agent 工具链与自主任务规划

### 4.1 LangGraph ReAct 状态机

Agent 用 LangGraph 的 `StateGraph` 构建，三个节点加一条循环边：

```
        ┌──────────┐    ┌───────────┐
        │  decide  │ →  │  execute  │ ──┐
        └──────────┘    └───────────┘   │ should_continue
              ↑                         │ （未 FINISH 且未达最大轮数 → decide；
              └─────────────────────────┘   否则 → synthesize）
        ┌────────────┐
        │ synthesize │ → END
        └────────────┘
```

- **decide**：把用户请求、已执行工具的结果摘要、剩余可用工具清单组装成规划 Prompt，要求模型输出 `{"action", "query", "intent"}`。其中 `query` 要结合已有结果重写，而不是照抄用户原句；
- **execute**：按工具签名构造参数调用，记录耗时和结果摘要；
- **synthesize**：把全部工具结果和串联链路交给模型生成最终回答，要求体现多工具结果的综合结论并标注页码。

### 4.2 八个 Function Calling 工具

| 工具 | 能力 | 触发场景 |
|------|------|---------|
| `rag_qa` | 文献库抗幻觉问答，带页码溯源 | 问已上传论文的内容 |
| `arxiv_search` | arXiv 实时检索 | 问最新进展、前沿方向 |
| `graph_analyze` | 引用图谱 + PageRank 基石论文 | 问核心论文、领域脉络 |
| `auto_survey` | 自动生成领域综述 | 要求总结领域现状 |
| `write_framework` | 生成七段式论文框架 | 有研究 idea 要成文 |
| `list_papers` | 列出文献库论文 | 问库里有什么 |
| `future_work` | 提取未来方向并剔除已被解决的旧 idea | 问不足、选题灵感 |
| `translate` | 中英互译，方向可由自然语言指定 | 要求翻译句子或段落 |

工具用 LangChain 的 `@tool` 装饰器定义，docstring 就是工具描述，直接进规划 Prompt。模型是靠读这些描述来决定调用顺序的，比如「帮我综述这个领域并找未来方向」会串成 `auto_survey → future_work → synthesize`。

这里还有一条最小必要工具原则：一次库内检索就能回答的问题（「某个概念是什么」）不再追加图谱、综述这类重工具，只有用户明确要多步分析时才继续调用。

规划 Prompt 里还内置了一张同义词映射表，limitation / 不足 / 展望 走 `future_work`，翻译 / 译为 / 译文 走 `translate`，最新 / 年份 走 `arxiv_search`。这一步是为了降低 7B 模型因为措辞差异漏调工具的概率。

`translate` 的 `query` 有固定格式，统一写成 `en | 待译文本` 或 `zh | 待译文本`，文本必须完整。用户用指代时（「把其中第一条翻译成英文」），规划器会从上文里把对应内容取出来再翻译，而不是把「其中第一条」当成待译文本。

### 4.3 决策鲁棒性设计

本地 7B 模型的 JSON 输出不太稳定，`_parse_decision()` 做了多层兜底：

1. 去掉 markdown 代码围栏后先按 JSON 解析；
2. JSON 解析失败，就在纯文本里扫剩余工具名、FINISH、DIRECT 关键词；
3. 工具名非法，或重复选择已执行过的工具，首轮默认回退 `rag_qa`，已有结果时直接 FINISH；
4. 双重终止：最大迭代 3 轮，或者全部工具执行完毕，任一条件满足就进入汇总，循环不会停不下来。

通用知识问题走 DIRECT 路由，不经过任何工具，由模型直接回答。但系统提示词要求它「不确定就说不知道，不要假装引用了文献」，与 RAG 路径的抗幻觉口径保持一致。这样做也避免了对文献库的无效检索。

### 4.4 思考链与多轮记忆

每一步都会记一条 `{step, intent, tool, query, output_summary, output_full, elapsed_ms, status}`，前端默认折叠、点击展开，能看到为什么调这个工具、传了什么查询、拿到什么结果、耗时多少。

多轮记忆按 session_id 保留最近 10 轮用户输入，后 3 轮摘要注入规划上下文。系统同时缓存上一轮的完整回答，遇到「把其中第一条翻译成英文」这类指代型追问时，会把上一轮回答原文一并交给规划器，避免指代落空。`rag_qa` 执行时拿到的 sources 也缓存下来，随 Agent 回答直接返回，不重复跑一次问答。

## 5. 抗幻觉设计体系

抗幻觉在这套系统里分四层落实：

| 层次 | 机制 |
|------|------|
| 检索层 | 距离阈值 0.9 过滤不相关内容；检索为空时直接返回「找不到」，不进生成环节 |
| 生成层 | Prompt 三条约束：只根据资料回答 / 标注论文页码 / 资料不足必须明说 |
| 校验层 | Future Work 的来源标题必须能对上库内真实论文（归一化模糊匹配），对不上就不展示；`solved_by` 必须是实际检索到的证据论文，判「已解决」但没有证据时自动降级为「部分解决」 |
| 呈现层 | 来源标签可点击跳转原文页，用户能即时核验；DIRECT 路径明确声明不引用文献 |

图表 Caption 也按同样的思路处理：模型拿到的是统计摘要，不是原始数据，编造具体数字的空间很小。

## 6. 关键创新点

### 6.1 语义级版本去重（top-1 mean 算法）

文献管理里有个真实痛点：同一篇论文的 arXiv v1 到 v7，或者重新导出后 MD5 变了，精确去重都会失效。这里的做法是逐篇已有论文做精准比对，用 top-1 相似度均值衡量整体重合度，再用相同 chunk 的数量辅助解释。阈值 0.90 和 0.70 是拿自比对、跨论文、版本对三组数据实测校准出来的，输出区分「高度重合」和「版本演进」两档，而不是简单的重复/不重复。

### 6.2 Future Work 时间线去重

做选题时最容易踩的坑是：论文里写的 future work，可能已经被后来的工作做掉了，照着做就是重复劳动。系统把这件事拆成五步：

1. **挖掘**：多路查询（future work / limitations / conclusion / open problems），提示词优先定位结论与展望段落，由 LLM 归纳 3–6 个带来源的方向；
2. **时间线**：LLM 推断各论文的发表年份并本地缓存（`_paper_years.json`，只有首次有开销），标题模糊匹配作为兜底；
3. **验证**：对每个方向在其他论文里检索相近片段，排除来源论文本身，距离小于 0.86 才算证据，收集真实证据标题；
4. **裁决**：用「严格审稿人」Prompt 逐条判定已解决 / 部分解决 / 仍开放；
5. **幻觉校验**：`solved_by` 必须能在证据论文里对上，否则「已解决」自动降级。

最终输出的是「仍开放 / 部分解决」的可做方向清单，已被解决的旧方向单独列出并说明由谁解决，配合论文时间线，直接回答「这个 idea 还能不能做」。

### 6.3 版式感知标题树

不依赖 PDF 书签，靠字号分布统计、粗体、排版方向和多模式噪声过滤重建章节结构。无书签的 arXiv PDF、带水印页眉的出版版本都能处理，粗体短行规则则补上了字号没有差异的模板。

## 7. 部署方案

### 7.1 本地开发部署

```powershell
# 后端（Python 3.13，需先启动 Ollama 并拉取 qwen2.5:7b）
cd backend && pip install -r requirements.txt
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000

# 前端（Node.js 18+）
cd frontend && npm install && npm run dev   # http://localhost:5173
```

### 7.2 Docker 部署

仓库内置 `docker-compose.yml`、`Dockerfile`、`nginx.conf`：

```bash
docker-compose up -d backend ollama                  # 后端 + 本地 LLM
docker-compose --profile serve-frontend up -d        # 前端静态资源走 nginx
```

### 7.3 低配置云服务器部署（公网方案）

线上环境是一台 2 核 2G 的轻量服务器，按 3 人左右轻量使用配置。

LLM 走云端 API，因为 2G 内存跑不了本地 7B 模型，设置 `LLM_PROVIDER=openai_compatible` 以及 `OPENAI_API_KEY`、`OPENAI_BASE_URL` 即可，业务代码不动。Embedding 仍是本地 ONNX MiniLM（23MB），CPU 推理没有压力。Chroma + FastAPI + ONNX 常驻约 300–400MB，541 页长文档全量解析时峰值约 1.1GB，因此配了约 4GB swap（两个 swap 文件）防止 OOM。

容器由 docker compose 统一托管，backend 跑 FastAPI/uvicorn，frontend 是 nginx 静态资源加 API 反向代理，用 `docker compose -f docker-compose.prod.yml up -d` 启动。域名未备案，对外用 8080 端口；站点登录由应用自带的登录页负责，除 `/api/auth/login`、`/api/auth/logout` 和 `/health` 外，未登录访问一律返回 401，登录成功后下发 HMAC 签名的 HttpOnly Cookie，有效期 7 天，评审账号随提交材料提供。nginx 的 `proxy_read_timeout` 调到 1800s，覆盖 541 页约 7–8 分钟的解析时间。向量库目录和上传目录用 volume 挂载，容器重启不丢数据。

### 8.2 语义去重阈值校准实验

| 比对对 | top-1 mean | 相同 chunk（≥0.98） |
|-------|-----------|---------------------|
| 论文自比对 | 1.0000 | 全部 |
| 不同领域论文两两比对 | 0.50 ~ 0.57 | 0 |
| Transformer v1 vs v7 | ≥ 0.95 | 绝大多数 |

据此确定 0.90（high_overlap）和 0.70（version_evolve）两档阈值。

### 8.3 Agent 多工具串联验证

几个典型用例见下。
「这个领域有哪些核心论文？帮我总结一下现状」串成 `graph_analyze → auto_survey → synthesize`，思考链里完整记录两步决策；「库里论文还有哪些可以做的方向」走 `future_work`，输出仍开放方向和已排除方向；「什么是注意力机制」属于通用问题，走 `DIRECT` 直接回答，不碰文献库。

连续追问「最新进展呢」时多轮记忆生效，`arxiv_search` 被正确触发；「把这些 limitation 翻译成中文」会串成 `future_work → translate → synthesize`，混合意图能连起来；「把其中第一条翻译成英文」回填上一轮回答原文，取到第一条内容后调用 `translate`。

### 8.4 自动化回归与并发压测

官方用例脚本 `tests/test_official_cases.py` 覆盖 T1–T10 共 10 个用例，包括上传解析、目录树、单页文本、版本演进识别、重复上传拦截、扫描件 OCR、长文档解析、RAG 问答、引用图谱和 arXiv 推荐，10/10 通过。Agent 侧回归覆盖 Future Work（显式/隐式）、英译中、中译英、混合意图等用例，多轮指代追问能正确复用上文；库外话题（如「今天天气怎么样」）和无依据问题全部拒答，并提示可以换个问法。

并发上传压测在腾讯云 2 核 2G 实例上做，3 篇 PDF 同时上传，期间再发起问答请求，12 次上传全部成功，无 OOM、无 5xx。问答在 CPU 满载时从 2s 涨到 18s，但请求没有丢失，内存峰值 1.1GB。

### 8.5 线上环境验收（2026-11-11）

部署完成后按演示路径逐项验证，数据来自线上实例：

| 项目 | 结果 |

## 9. 局限与未来工作

### 9.1 已知局限

1. **扫描件 OCR 精度**：扫描件走 Tesseract 中英双语识别，低分辨率或复杂版式下会有字符错误，版面标题树识别也有限，目录可能为空。后续可以换 PaddleOCR 或版面分析模型；
2. **引用匹配精度**：references 用词元重合度（≥75%）匹配，缩写标题、同名变体仍会漏配，引入 GROBID 这类结构化解析可以改善；
3. **多轮记忆**：进程内字典实现，服务重启就丢失，生产环境应换成 Redis；
4. **年份推断**：Future Work 的时间线依赖 LLM 推断发表年份，冷门论文可能不准，可以接 arXiv 或 DOI 元数据校正；
5. **向量索引自检**：目前没有启动时的索引完整性校验，前面提到的索引残缺只能靠人工发现。

### 9.2 规划方向

- 扫描件 OCR 换用 PaddleOCR / 版面分析模型，提升低质量扫描件的识别率；
- 引用抽取引入 GROBID 等结构化解析，提升缩写标题和多作者文献的匹配精度；
- 增加更多图表类型（如三维雷达图）和批量实验数据对比模板；
- 服务启动时校验向量库索引完整性，发现缺块自动重建。
